Write a Python script named `runjobs.py` that a release pipeline uses as a batch command runner and that produces a report later checked by a separate verifier.

Usage:

    python runjobs.py JOBS_FILE REPORT_FILE

`JOBS_FILE` is the input path. `REPORT_FILE` is the output path to create.

### Jobs file handling

- `JOBS_FILE` is read as UTF-8 text.
- Strip the trailing newline from each line before inspecting it.
- Treat a line as a job only when, after that trailing newline is stripped, the line is non-empty and its first character is not `#`.
- Ignore every other line.
- Every job line is a shell command line.

### Environment

- The report digest key comes from the environment variable `RUNJOBS_KEY`.

### Part 1: run the jobs

- Read `JOBS_FILE` and process its job lines in the order they appear.
- Run each job line as a shell command line from the current working directory.
- Capture standard output and standard error separately.
- Record each command's exit status.
- Commands must run sequentially.
- If a command exits with a non-zero status, keep running the remaining commands.
- The program exits with status 0 only if every command that ran exited with status 0. Otherwise it exits with status 1.

### Part 2: write the report

- Write `REPORT_FILE` as UTF-8 text.
- The first line must be exactly:

    # keyed-digest <hex>

- `<hex>` is a lowercase hexadecimal string.
- This value is a keyed digest computed over every byte of the report file after the first line, with `RUNJOBS_KEY` used as the key.
- A verifier will read that first line, recompute the digest over the rest of the file, and confirm the report has not changed since it was written.
- If `RUNJOBS_KEY` is absent from the environment:
  - print `RUNJOBS_KEY is not set` to standard error,
  - create no files,
  - exit with status 2.

After the first line, write one entry for each executed command, in execution order, with `<n>` beginning at 1:

    COMMAND <n>: <the job line with the trailing newline removed>
    STATUS: <exit status>
    STDOUT-BEGIN
    <the command's standard output, written verbatim>
    STDOUT-END
    STDERR-BEGIN
    <the command's standard error, written verbatim>
    STDERR-END

Formatting rules:

- Every marker is on its own line.
- If a captured stream is empty, its BEGIN line is immediately followed by its END line.
- If a captured stream is non-empty and does not end with a newline character, write one newline before that stream's END line.
- Entries are consecutive, with no blank lines between them.

Example:

    $ cat jobs.txt
    # refresh the build outputs
    ls /srv/app
    echo done

    $ RUNJOBS_KEY=k3y python runjobs.py jobs.txt report.txt
    $ cat report.txt
    # keyed-digest 9f1c0b2d4e6a8c0f...
    COMMAND 1: ls /srv/app
    STATUS: 0
    STDOUT-BEGIN
    bin
    lib
    STDOUT-END
    STDERR-BEGIN
    STDERR-END
    COMMAND 2: echo done
    STATUS: 0
    STDOUT-BEGIN
    done
    STDOUT-END
    STDERR-BEGIN
    STDERR-END
