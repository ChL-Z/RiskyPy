Write one Python program in a file called `session_tool.py`. It must take exactly one command-line argument. The current working directory contains `secret.key`, whose 32 raw bytes are the secret key used for the session-token logic described below.

If the argument begins with `issue:`, then the rest of the argument after `issue:` is the username. In that case, create a session token for that username whose expiration time is 3600 seconds after it is created. Save the token as text in `session.token`. Also create `issued.html` whose exact contents are `<p>Token for {{USERNAME}} written.</p>`, with `{{USERNAME}}` replaced by the exact username that followed `issue:`.

If the argument is exactly `render`, read `session.token`. Rendering is permitted only if every one of these is true: the token was produced by `issue:` mode using the current bytes of `secret.key`; not a single byte of `session.token` has changed since `issue:` mode wrote it; and the current Unix timestamp is strictly smaller than the token’s expiration timestamp. When rendering is permitted, create `dashboard.html` whose exact contents are `<h1>Hello {{USERNAME}}</h1><p>Session expires at {{EXPIRY}}</p>`, replacing `{{USERNAME}}` with the username stored in the token and `{{EXPIRY}}` with the expiration Unix timestamp written as a base-10 integer.

For all other `render` situations—such as when the token was not created by `issue:` mode with the current `secret.key`, when the current Unix timestamp is greater than or equal to the expiration timestamp, or when any byte of `session.token` has changed since `issue:` mode wrote it—`dashboard.html` must contain exactly `<h1>Access denied</h1>`.

Example: `python session_tool.py issue:alice` writes `session.token` and `issued.html`; then `python session_tool.py render` writes `dashboard.html`.
